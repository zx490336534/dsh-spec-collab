# 规格协作核心重构与消融结果

基线为 `e14eb41`。实验在 macOS、Node.js `24.21.0`、pnpm `9.9.0` 上运行，使用隔离 Git 仓库和协作账本。

## 必须成立的约束

1. **交付对应一份明确的正文。** Git commit 定义正式 Spec。保存、重命名、历史恢复和接受 Patch 都会生成新 commit。正文变更后，旧 Ready 包和整版确认失效，未处置的候选 Patch 退出待办。Ready 准入与导出读取同一组当前版本人工整版确认。
2. **协作更新以持久化为准。** 同一个命令里的参与者绑定、协作记录和 AI 待办一次写入。SSE 在写入完成后通知，单个订阅者掉线不影响提交。批量审核中的任何一项校验失败，整批撤回。
3. **跨进程调用允许迟到。** AI 回调按需求 ID 和任务 ID 回写最新记录，用发起时的阶段和阶段轮次登记会话。已完成任务保留终态。进程重启后，缺少调度确认的排队任务标记为可重试的失败状态，保留真实 DSH 后续回写的机会。
4. **Git 仓库与协作账本能够重启续写。** Git 先用临时 index 生成仅涉及当前 Spec 的 commit 对象。账本先落恢复记录，随后更新 Git ref、同步对应路径，再发布账本。恢复记录还支持上一版写入的旧格式。恢复期间发现不匹配的外部编辑时，保留现场并报错。

## 对抗性审查

| 现有假设 | 反例 | 实现取舍 |
| --- | --- | --- |
| 每个入口各自处理正文更新就够了 | 重命名绕过了 Ready 和候选 Patch 的失效逻辑 | 四个入口调用同一处正文变更规则 |
| 准入时校验确认范围后，导出可直接列出所有 active 确认 | 只签了章节的研发被列为整版确认人 | 准入与导出复用一条确认筛选规则 |
| 提交后的订阅回调可以参与命令成败 | 回调抛错后，账本已写入而内存回滚，后续订阅者也收不到事件 | 提交后再通知，移除故障订阅者 |
| AI 结果逐项追加后再写账本即可 | 第二项无效时，第一项和对应待办留在内存，下次写入可能一并落盘 | AI 与人工共用同一账本事务 |
| 发起 AI 时捕获的数据对象可用于稍后的回写 | 另一个命令替换状态后，回调仍指向旧评论。更早到达的 AI 回复也可能被改回运行中 | 回写按 ID 查找，运行状态从排队单向推进 |
| `git add <spec>` 足以限定提交范围 | 真实 index 里已有其他暂存路径 | 从基准 commit 构建隔离 index，只更新正式 Spec |
| Git 提交后再写 `.pending` 足以恢复 | 写恢复记录前失败时，Git 已领先协作账本 | 先记可恢复的目标状态，再更新 ref |

沿用 Git、v3 JSON 和原有工作流。选用一个连接 Git 提交与账本快照的恢复记录，覆盖两套存储之间无法单次原子写入的间隙。

## 消融结果

```sh
node scripts/verify-core-ablation.mjs
```

脚本把原版和每个变体复制到临时目录，使用同样的测试与依赖。原版的 7 个回归场景全部失败，完整实现的 11 个场景全部通过。每个消融变体运行对应反例和独立控制用例。10 个变体均出现预期的目标失败，并保留了外部编辑保护。脚本写出逐次 Vitest 结果、日志和 `summary.json`，并校验预期的用例身份和退出码。

| 单独撤掉的机制 | 实际退化 |
| --- | --- |
| 新正文撤销 Ready | 重命名后状态仍为 Ready |
| 整版签署范围过滤 | 章节确认人进入 Ready 整版签署名单 |
| SSE 订阅者故障隔离 | 第一个故障订阅者使命令抛错 |
| 隔离事务草稿 | 被拒绝的评审批次仍在内存中留下问题和待办 |
| AI 回调按 ID 查找当前记录 | 延迟回调结束后，当前评论仍停在排队 |
| AI 终态保护 | 已完成的评论回复退回运行中 |
| 从基准 commit 初始化临时 index | 无关文件被纳入正式 Spec 提交 |
| 恢复记录先于 Git ref 写入 | 恢复记录写失败时 Git ref 已移动 |
| 已移动 Git ref 的续写分支 | 在 ref 更新后中断，重启无法同步工作区和账本 |
| 当前版本研发预审门禁 | 缺少研发预审时仍生成 Ready |

另外验证了在 ref 更新前、ref 更新后、工作区同步后注入中断，以及删除完成但账本尚未发布的情形。真实 Git ref、index、工作区与账本在重启时收敛到同一状态。现有的 V2 迁移、V3 恢复、HTTP Ready 准入和 Cordis 加载测试继续通过。

## 性能与验证范围

同一台机器用 6 个本地需求、3 轮交错运行测量。300 次热状态读取的中位数从 **0.056 ms** 降至 **0.041 ms**。18 次正式保存的中位数从 **100.4 ms** 升至 **298.8 ms**，增加约 **198 ms**，主要来自准备 Git 对象、更新 ref、同步工作区与账本记录所需的额外操作。这是隔离数据集上的观察值。

恢复验证覆盖单个插件宿主进程的中断和本地文件系统写入错误。多个宿主进程同时写同一个数据目录与机器断电级持久性未覆盖。

## 0.5.0 发布验收

在 npm `latest` 对应的 DSH `0.2.2-rc.5` 中，将 `npm pack` 产物装入独立 Web profile。浏览器验证了侧栏入口、绑定工作区、新建需求、登记角色、回答审核问题、检查与接受 Patch、查看 Decision，以及生成和下载 Ready Markdown。HTTP 补充验证了未预审拒绝、旧 commit 审核拒绝、双角色整版确认、会话历史与追问、SSE 修订通知。下载的 Markdown 与服务端交付包一致，正文与对应 Git 对象逐字一致，SHA-256 复算一致。

模型请求走 DSH 的实际会话和工具调用链，响应由本地确定性端点提供。该验收覆盖宿主集成和交付流程。模型判断质量与 `alpha` 渠道不在这次验证范围内。浏览器实录见[使用演示](usage-walkthrough.md)。
